# External Skill Packs: Roles, Modes, And Boundaries

Use this reference when a launch routes work to an installed third-party skill pack. It names the pack, the roster role that may load it, the mode (producer or auditor), and the boundary that keeps B2C App Builder the owner of graph execution, evidence, and done gates.

The rule this file exists for: a skill pack never marks a lane done. B2C references that already adapt a pack win on conflict. Record each pack a launch uses in `strategy/TOOL_DECISIONS.md` and `engineering/ENGINEERING_PLAN.md`.

Packs install under `~/.agents/skills` for Codex and Cursor, with symlinks into `~/.claude/skills` for Claude Code. Skill names below are the installed directory names. Verify the installed set with the current runtime's skill listing before dispatch. An unavailable optional pack never blocks work; the B2C reference that adapts it stays the contract.

## Producer And Auditor Modes

- A producer loads a pack to make something. Its output is product.
- An auditor loads a pack to score something. Its output is findings.
- The same agent never holds both modes for one surface. `reference.orchestration.isolated-review` owns the isolation contract.
- A pack that writes B2C-owned files (`PRODUCT.md`, `DESIGN.md`, reducer state) is restricted to the commands that do not.

## Out Of Scope

Packs that exist locally but do not match the selected stack stay unloaded: Expo, React Native, and Flutter packs on a SwiftUI launch; Play Store packs on an iOS-only launch; general image-generation and taste packs that duplicate a routed pack. Record the exclusion once in `strategy/TOOL_DECISIONS.md`.

## Recording

- `strategy/TOOL_DECISIONS.md`: one row per pack used, with role, mode, and the date the installed set was verified.
- `engineering/ENGINEERING_PLAN.md`: the packs the engineering lane relies on, and the auditor that runs `intended-vs-implemented`.
- The knowledge receipt on every dispatch names the pack skills the worker loaded.
