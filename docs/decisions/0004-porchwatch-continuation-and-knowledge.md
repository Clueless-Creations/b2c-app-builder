## Decision

A complete-business request retains its scope through research, design, implementation,
independent review and closeout. Routing projects the existing catalog dependency graph;
it does not introduce successor fields or another scheduler. `operations/LAUNCH_PROGRAM.md`
retains the opening request. A provisional registered workspace identity is not a final brand.
A bounded session may pause for context, resources or authority without completing the business.
The public plan/run project delivery acceptance independently from successful node counts.
Research-only requests remain research-only.

Knowledge delivery schema 2.0 is route-first. Authored Markdown remains the source. Explicit
`include: instructions` returns workflow instructions; `summaries` and `full` retain the
bounded allocator and its truncation reporting. Route metadata includes exact artifact
specifications, validator commands and required reference resolvers. Section identities are
scoped to the full-document content hash. An old section selector against changed bytes refuses.
Discovery or bytes delivered never establishes that the agent read or correctly applied guidance.

`specifies` lives in the existing knowledge manifest. It binds an artifact's specification to
its producers and generates exact section resolvers. The validator must not be the only spec.
Local and hosted tools share these rules. Hosted knowledge remains workspace-free and read-only.

Planning research validates content without reducer state. The absence of runtime state in a
valid planning workspace is expected; missing or malformed state after initialization is not.
The normal initializer remains the only route to execution state. Planning query checkpoints
are immutable, bounded source observations under the research corpus, not a second scheduler or
accepted-evidence store. They use registered targets, workspace revision checks and the existing
session lease. Pending or uncertain queries require readback before a new dispatch intent.
No cache lookup calls a provider, proves a claim, or grants spend authority.

## Product and evidence policy

The authored scope is a complete deliverable within the accepted promise. Narrow products and
explicit non-goals are legitimate. Deferring a required integration or design obligation is not
an alternative completion state. Internal incremental builds and simulator tests remain useful;
a test preview is not the delivered product. Live effects still require their normal authority.

The active reference is `reference.product.core-loop-and-complete-scope`. The previous
`core-loop-and-v1-scope` identity is intentionally retired because its contract taught required
work deferral. Current authored bindings and projections use the replacement. Historic installed
snapshots are not edited or repinned. Legacy `copy.v1_boundary` input normalizes to `completeScope`;
new authoring uses `copy.complete_scope`. Supplying both fields refuses. API versions and genuine
quoted historical vocabulary are not subject to a blind global replacement.

Frozen design calibration rubric schema 2 records resolution status and observation time for
selected source artifacts. Explicitly expired, unavailable or unverified sources cannot support
a lock. A valid retained snapshot does not depend on a signed URL staying live indefinitely.
An alternative must cover the required evidence kind; a guide is not a visual or interaction
observation. Provisional exploration can continue while mandatory lock evidence remains blocked.

A proposed price can be a research hypothesis. Canonical `class.price` instances and active
revenue work require current offer evidence or the existing explicit founder waiver. The general
opening build mandate is not exact pricing authority. This content validation does not replace
host enforcement of legal/pricing effects. No new revenue-estimate confidence threshold is
invented in this repair; confidence, limits and the existing decision policy remain explicit.

## Verification and limits

Fixtures cover route continuation, section retrieval without filesystem access, stale revisions,
planning validation, fresh-process evidence reuse, uncertain request refusal, resolved design
sources and pricing evidence. Runtime acceptance continues to require actual artifact and review
proof through existing owners. Fixture results do not establish a live Porchwatch rebuild,
provider API success, device quality, market demand or production launch readiness.
