# Portfolio Registry

One page across every business the founder runs. Create this the day a second `state/business-state.json` exists, keep it in the founder's own workspace (not inside any single app's repo), and refresh it at each app's day-30/day-90 retro checkpoint — the same moments the Kill-Or-Scale Review runs (`post-launch-operations.md` §9). This is where a repeat founder sees the whole board: which app deserves the next hour, which one is quietly winning, which one should be wound down so the next idea gets its slot.

Two rules keep the registry honest:

- Every row's numbers come from that app's own records (RevenueCat, PostHog, the weekly log) — never from memory.
- Names, brand vocabulary, tokens, domains, and credentials never move between businesses. Learnings, engineering patterns, and any audience the founder owns outright do.

Stage is the app's current phase in plain words (building, in review, live, winding down). Last verdict is the most recent Kill, Hold, Or Scale decision from that app's `operations/LAUNCH_RETRO.md`.

## Allocation

Where the founder's hours and any paid spend go this month, and why. One paragraph, updated when a verdict changes it. The default rule: the app with the strongest verdict gets the marginal hour; an app on Hold gets its weekly rhythm and nothing more; an app being wound down gets only its subscriber and legal obligations.

## Cross-App Learnings

What one launch taught that the next one uses. Fill this from each `operations/LAUNCH_RETRO.md` as it lands — category economics that surprised, funnel numbers worth reusing as baselines, channels that worked, plays that transfer. Entries name the source app and date so a future launch can weigh how current the lesson is.

Each entry: the idea in one line, the evidence that makes it credible (category numbers, social language, competitor gap), and what would need to be true to start it.
